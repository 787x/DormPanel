# PR73：课程 Widget 缓存有效期

基线 2f8facc。只更新 PR73，保留独立滚动、教学周判定、选择标识及同步快捷入口。

## 有效性统一

Snapshot 增加 capturedAt 与 validUntil，和 CollectionBasis 一起判定：日期、ZoneId 匹配，当前时间不早于生成时间且严格早于有效截止。向后调时同样会失效。近日截止复用两日 Day.next 的较早值，包含课程开始／结束及下一自然日；不另写时间计算规则。周快照保存日期／时区基准，截止为该时区下一自然日，因此同周跨日、跨周、时区变化都会失效。

available、instanceSnapshot、Factory.getCount/getViewAt 共用此有效性。过期时返回空行／原有刷新状态，旧周网格不再仅因 grid 非空而被接受。周组件的日期标题也来自快照基准；适配器身份包含日期、时区及配置，旧日期／旧配置 Factory 不会读取新的不相干网格。Factory 按创建时捕获的周配置精确读取对应缓存。

同日课程边界后的正常刷新保持适配器身份和稳定行 ID。Factory 在收到新的有效快照后重新允许下一次失效请求，避免只在第一次边界能刷新；无有效新快照时仍不会逐行不断请求。所有缓存需求继续 ensure，真实更新继续 request。没有修改协调器 generation、超时、两个物理任务上限，也没有新增计时器、轮询、Store 或线程。

复用核心 ScheduleClock，默认 DeviceScheduleClock。测试临时替换隔离进程的时钟并在 finally 恢复，未修改系统时间或给产品增加时钟配置。

## 本轮实际验证

- Phone 构建、Lint、58 项 JVM 全部通过。新增 3 项有效期测试覆盖 09:00 的 A(08:00–09:50)／B(10:10–12:00)、09:40 复用、09:50 精确失效及重投影去掉 A、明日保持、向后调时；周日到周一、时区变化；纽约夏令时结束的 25 小时自然日（24 小时后仍在同一天，不提前过期）。
- API 28 Android 共 3 项通过：新增受控时钟过期读取计数／适配器保护测试，加上已有双 Factory 冷热缓存、真实更新入口及失败恢复测试和午夜一致性测试。
- 新测试在真实 Factory 对象与隔离 Fake Store 的 loadPresentation 入口计数。09:00 创建、09:40 再创建均 0 次额外读取；09:50 两列拒绝旧行（getCount=0、getViewAt=null），共 1 次读取；完成后左列仅 B，右列行内容和身份不变。
- 再推进到 10:10，两个原 Factory 仍可请求下一次刷新，共第 2 次读取；叠加正式提交通知后旧结果被拒绝，第 3 次读取发布 B-new。这里是正式通知入口＋Fake Store 的可控场景，不是真实数据库提交。
- 周日进入周一触发第 4 次读取，网格 monday 和 today 均切到新周一；旧周日 Factory 即使收到新数据仍返回 0，且不因它再次增加读取。
- 同周周一进入周二，两个周 Factory 同时检测过期，只增加第 5 次读取，today 更新。时区变化后两种 available 均为 false，共第 6 次读取；失败后合并重试为第 7 次并恢复。
- 五天实际时间模式以主线程受控发布检验：精确取得五列时间轴，新配置 Factory 可读且不增加物理读取，旧七天节次 Factory 不返回该数据。早期将此配置断言和 Host 的异步通知混在固定步骤计数中未取得预期网格，未计为 PASS；最终把该配置身份检查单独放进一次受控发布，过期及正式通知部分仍经实际 Fake Store 读取计数。

测试用未来日期的周日及后续日推进时钟，避免隔离包的 RTC alarm 被置于真实系统时间的过去；未调系统时间，最后恢复默认时钟、模式和正式 Store。测试只更新 .pr72testbed，不改日用 APK／数据库。

## 范围与未实测项

本轮未新增 MIUI 触控、真实 Launcher 自然 09:50／午夜、系统休眠下刷新时延或真实 WebDAV 验证；已渲染在 Launcher 客户端的旧画面仍受原有非精确更新时延影响，不能承诺边界时刻瞬时消失。本轮证明的是有效性路径及 Factory 再请求时拒绝过期数据、合并必要读取；不是用静态代码推断替代设备时延实测。无关布局／独立滚动／选择状态／同步快捷按钮验证复用前轮记录。
